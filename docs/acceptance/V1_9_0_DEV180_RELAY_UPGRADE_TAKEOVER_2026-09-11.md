# VibeKits dev.180 中继升级接管验收

## 真实故障证据

- 目标机前台运行 `dev.179`，LMCP/2 广播、TLS 指纹固定、197 个工具目录、
  仿真状态和进程读取均通过。
- 目标后台 `vibekits-harness-relay --vibekits-harness-service` 仍来自旧安装
  目录，导致 routing ID `4456560334` 的 P2P/中继字节通道持续超时。
- 旧逻辑只检查服务“是否可调用”，没有确认它是否来自当前安装包。

## 修复

1. 仿真开关继续独立持久化，并新增当前包内中继二进制 SHA-256 指纹。
2. App 根生命周期恢复仿真能力时，对比已运行版本与当前包指纹。
3. 首次升级迁移或指纹变化时，安全停止旧服务、确认退出、启动当前包内
   服务，再开放固定回环 MCP 端点 `127.0.0.1:32147`。
4. 指纹一致的普通启动不重启中继，不影响 Harness 首帧和现有工作区。

## 自动门禁

- 保存开关与中继指纹持久化。
- 普通启用、关闭、连接状态与回环 MCP 端点生命周期。
- App 根恢复不依赖 Harness 页面。
- 升级恢复必须恰好停止一次旧服务并启动一次新服务。
- `flutter analyze --no-pub` 必须无问题。

## 真机复验门禁

目标机安装并启动 dev.180 后：

1. 后台中继进程路径必须来自当前 dev.180 安装目录。
2. 按 routing ID 建立 `32147` 隧道并完成 MCP `initialize`。
3. 完成 `tools/list`、`vibekits.device.processes` 和短窗口
   `vibekits.device.logs` 只读调用。
4. 关闭控制端隧道后，本地临时监听端口必须消失；目标 Harness 页面不得
   被打开、覆盖或重启。
