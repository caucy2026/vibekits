## 1. 已定位根因

远程协助的首次证书配对和正式会话分别使用固定回环目标 `127.0.0.1:32145` 与 `127.0.0.1:32146`。旧 RustDesk 配套引擎只为远程仿真的 MCP `32147` 和 SSH `22` 提供受控快速路径；远程协助两端口仍落入普通 TCP 隧道权限判断，目标端返回 `No permission of IP tunneling`，控制端最终只看到 `HARNESS_TRANSPORT_transport_connect_timeout`。

这不是 UI 等待时间、用户没有点击批准或 TLS 证书内容导致的问题。连接在证书配对请求到达执行端以前已经被错误权限门禁拦截。

## 2. 修复边界

- RustDesk 引擎新增独立控制命令 `--vibekits-harness-remote-assistance-access`。
- 远程协助只允许固定目标 `127.0.0.1:32145`、`127.0.0.1:32146`；远程仿真仍只允许 `127.0.0.1:32147`、`127.0.0.1:22`。
- 两个开关使用独立原子状态。关闭远程仿真不会误停远程协助，关闭远程协助也不会开放 SSH/MCP 仿真权限。
- 普通远程桌面、文件传输、终端和任意 IP/端口没有获得旁路权限。
- VibeKits 打开、恢复和停止远程协助时显式同步该原生授权；停止后撤销授权，仅在仿真也未使用时停止共享中继进程。
- 升级启动时如检测到旧 Relay 不认识新的远程协助控制命令，会先通过受控停止命令结束旧服务，再从当前 App 包启动精确同版 Relay 并重试授权；若远程仿真原本开启，会同时恢复其原生授权。关闭远程协助时则保持失败关闭，不会为了关闭操作重启服务。
- 控制端生命周期仍绑定 stdin EOF；异常退出不会遗留旧目标隧道。
- 协同和仿真均关闭且无真实控制会话时，Harness 主界面不显示黄色连接信息或异常状态。
