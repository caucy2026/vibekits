## 1. 已通过的真实远程仿真

控制端使用本机 VibeKits 配套 Relay，仅输入目标统一 ID `4456560334` 建立受管隧道。以下两条路径分别独立运行成功：

- 默认路径：P2P 优先、失败自动回退中继；远端公开 `195` 个 MCP 工具，成功调用只读 `vibekits.device.processes`。
- 强制中继路径：`forceRelay=true`，经 HBBR 建立相同 MCP 会话并完成同一只读调用。
- 两轮结束均主动关闭控制器；强制中继后原生连接查询返回 `state=idle`、`connections=[]`，没有把一次验收遗留为后台连接。

以上证明的是“远程仿真 MCP”链路，不等同于“协同项目/会话”链路。

## 2. 协同首次配对的真实阻塞

对同一目标发起协同配对时，先后得到过 `PAIRING_CHANNEL_CLOSED` 和原生明确拒绝 `VibeKits managed Harness access is disabled`。随后通过已授权的远程仿真 MCP 调用协同开启接口，最终定位为：

```text
REMOTE_PAIRING_SCOPE_NOT_PERSISTED
```

现有实现把“已经持久化配对范围”错误地作为首次开启执行宿主的前置条件；但首次批准之前不可能存在该范围，形成生命周期死锁。正确边界应为：

1. 未配对时只启动固定 `32145` 的最小配对监听；
2. 密码校验与目标用户明确批准成功后，才持久化控制端证书及最小工作区范围；
3. 只有已批准证书才能进入固定 `32146` 的项目、会话与命令通道；
4. 关闭协同必须撤销两个固定端点，且不得影响独立的仿真 `32147/22`。

用户已明确要求在打开远程协助时强制启动配对载体。实现只把“尚无首次批准范围”解释为等待配对；不得绕过配对范围、用 shell 修改配置或把仿真权限冒充协同权限。Relay、固定监听或后端的其他真实启动错误仍必须失败关闭并回滚开关。
