# Vibekits 能力融合与智能体自动发现最高准则

版本：1.0

生效日期：2026-08-20

本文件是新增、移植和重构任何工具能力时的最高设计准则。若功能实现、界面草图或第三方项目习惯与本准则冲突，以本准则为准。

## 1. 唯一目标

Vibekits 不是工具启动器，而是一个共享上下文的开发工作台。新增能力必须同时满足：

1. 用户在当前任务里自然到达，不需要理解第三方工具名称。
2. Harness 能从能力目录自动发现何时使用、何时不使用和需要哪些参数。
3. 手工界面与智能体调用共用同一领域服务、目标句柄、权限、取消和结果类型。
4. 结果能继续流向下一个合适能力，而不是执行完后成为孤立文本。
5. 默认离线、后台、有界、可审计；敏感数据不进入模型参数和日志。

## 2. 单一能力清单

`ToolSpec` 是微工具、界面搜索、Harness 发现和模块日志的单一注册源。不得再分别维护“界面工具表”“Harness ID 表”和“日志 ID 表”。

每项能力必须声明：

| 字段 | 作用 |
|---|---|
| `id/name/group/description` | 稳定身份、用户名称、融合位置和结果含义 |
| `run` 或 `runAsync` | 唯一领域执行入口；耗时任务必须使用后台实现 |
| `aiUseWhen` | 模型应优先选择该能力的真实场景 |
| `aiAvoidWhen` | 容易误用、越权或结果不可靠的场景 |
| `aiExamples` | 1～3 个用户意图示例，不包含秘密或固定机器路径 |
| `harnessToolIds` | 复杂工作区对应的一个或多个工具 ID；同构微工具可省略并自动得到 `vibekits.<id>` |
| `offline/risk/schema` | 网络边界、权限级别和结构化输入合同 |

新增带 `run/runAsync` 的微工具后，构建时自动完成：

```text
ToolSpec
  ├─ “转换与检查”分类与搜索
  ├─ Harness executable catalog / MCP tools/list
  ├─ 使用场景 + 禁用场景 + 本地优先描述
  ├─ 当前模块 Harness 调用日志
  └─ 开发工具—Harness 一致性合同测试
```

因此禁止为了新微工具手工修改 Harness 系统提示词。Harness 在任务会话建立时读取 MCP `tools/list`；新版本加入能力后，名称、描述、参数 Schema 和使用边界随目录一起出现。复杂硬件/远程工具仍需显式适配器，但 ID 只能声明在 `ToolSpec.harnessToolIds`，界面和日志直接复用该声明。

## 3. 智能体选择规则

1. 能用 Vibekits 本地工具取得确定结果时，优先工具调用，不用 shell 猜测，也不让模型凭记忆计算。
2. 先使用低成本、只读、范围最小的能力。例如先“代码统计/文件搜索”，再决定是否读取具体源码；先“JSON 路径查询”，再把小结果送入模型。
3. 工具描述必须写任务意图，不能只写实现名。例如写“从 API 响应提取字段”，不能只写“jq”。
4. 模型不得自动把读取升级为修改。搜索、统计、Diff 的结果只能成为写操作的输入候选，写操作仍走独立权限合同。
5. 密码、API Key、私钥、串口密钥和数据库凭据由 App 安全存储注入，不能由模型读取、回传或写日志。
6. 工具失败必须返回可行动错误；模型可以调整合法参数或建议用户操作，不能伪造成功结果。

## 4. 融合而不是新增孤岛

每个能力至少设计一个上游和一个下游：

- 代码统计 → 找出主要语言/大目录 → 文件搜索、Diff 或 Harness 分析。
- 文件搜索 → 打开/定位 → Diff、哈希、压缩或交给 Harness。
- API/数据库响应 → JSON 路径查询 → Diff、保存或继续推理。
- SSH 登录 → 同一认证会话 SFTP → 下载文件后 Diff/哈希。
- ADB/串口日志 → 搜索/过滤 → 交给 Harness 解释；目标设备保持绑定。
- OCR → 文本查询/保存/对比 → 回到原 Harness 会话。

若找不到真实上下游，该能力默认不进入一级或二级导航，只保留为候选研究项。

## 5. 执行、权限与日志

- UI 线程只做渲染和轻量状态；目录扫描、哈希、解析、网络、设备和子进程都在 Isolate/worker/独立进程中运行。
- 每项操作声明输入上限、结果上限、超时和取消；禁止把无限目录、完整日志或超大响应一次送给模型。
- Harness 工具日志默认开启，可按模块关闭并可删除。关闭一个模块不得影响其他模块。
- 日志记录工具 ID、目标、脱敏参数、开始时间、耗时、状态和有界结果摘要；不记录文件正文、图片像素、密码、Key 或完整模型输入。
- 手工入口与 Harness 必须由真实执行器记录同一种证据，不能由聊天层伪造“已调用”。

## 6. 开源吸收准则

1. 先吸收任务模型、算法和测试思想，再决定是否分发二进制；不复制第三方品牌和整套 UI。
2. 只引入许可证清晰、维护活跃、Windows/macOS 可验证的依赖。版本、许可证、来源、修改和资产哈希进入供应链文档。
3. 已有领域服务能覆盖时不重复打包。例如 ripgrep/fd 的忽略和有界搜索原则融合到文件搜索；delta 的可读 Diff 原则融合到文件 Diff。
4. 任意命令执行、全盘改写、证书替换、网络代理等高风险能力不能因为项目 Star 高就直接接入。
5. 第三方二进制必须随 Release 自包含、固定版本并验证哈希；运行时禁止临时下载。

## 7. 必过验收门禁

每个新能力必须具备：

1. 领域层真实输入/失败/边界测试。
2. 主流操作路径的界面测试；纯微工具至少有统一集合工作区测试。
3. Harness `tools/list` 可发现和真实 `invoke` 测试。
4. ToolSpec 声明的全部 Harness ID 均进入可执行目录的合同测试。
5. 默认日志、模块关闭、敏感值脱敏和删除记录测试。
6. Analyze、Windows Release、自包含资产及版本报告；涉及硬件/远程服务时另列真实环境证据，不能用模拟测试冒充。

任一项缺失，只能标记“实现中”，不得进入已完成清单。

## 8. 当前优先序

| 优先级 | 上游参考 | Vibekits 融合方式 |
|---|---|---|
| 已落地 | ripgrep / fd | 复用现有文件搜索，继续补 `.gitignore` 语义和有界并行，不增加新入口 |
| 已落地 | tokei | “转换与检查 → 文件工具 → 代码统计”；项目摘要可直接供 Harness 决策 |
| 已落地 | jq | “转换与检查 → 格式处理 → JSON 路径查询”；先提取小结果再推理 |
| 已落地 | delta | 文件 Diff / Git Diff 共用可读差异结果，不打包另一套界面 |
| 下一批 | ast-grep | 结构化只读搜索优先；改写必须单独预览和批准 |
| 下一批 | yq | 在统一结构化查询中扩展 YAML/XML/TOML，不增加独立 yq 页面 |
| 评估中 | hyperfine | 只允许用户确认的可执行文件和参数模板；禁止模型任意 shell benchmark |
