# VibeKits 统一 ID 远程仿真需求与验收规范

## 1. 用户场景

设备 A 安装了 VibeKits 和一个或多个待调试 App。待调试 App 出现崩溃、卡死、性能异常或兼容问题时，设备 B 上的开发者或智能体只需知道 A 的 VibeKits 数字 ID，并在 A 已明确打开授权开关的前提下，把 **A 整台机器** 当作远端真机/仿真机使用。被调试对象是 A 上的其他 App 和系统运行环境，不是 VibeKits 自身；VibeKits 只提供身份、加密通道、工具目录、权限撤销和审计。源码可以只存在于 B；日志、进程、崩溃、性能和实际执行结果必须来自 A。

远程协助 ID 与远程仿真 ID 必须是同一个由 VibeKits 内置 RustDesk 网络引擎注册并经 HBBS 确认的数字 ID。不得再生成第二个设备号，也不得要求用户理解 IP、端口、SSH 密码、密钥、证书或中继地址。

## 2. 产品目标

1. A 默认只显示本机 ID，“允许作为仿真机”默认关闭。
2. A 打开一个开关后即完成授权和服务准备；界面显示准备中、可连接、已连接、异常四类真实状态。
3. B 输入 A 的 ID 后优先局域网 P2P，打洞失败自动使用 HBBR 原字节中继。
4. B 上的大模型收到 ID 后自动连接、读取 A 当前真实的 MCP 工具目录并自行选择工具，获得目标 App 发现、进程、实时/历史日志、崩溃报告、CPU/内存/磁盘、截图、受控文件、应用安装/启动/停止及必要调试能力。
5. A 关闭开关后立即拒绝新调用、关闭既有仿真机端点和受管隧道、撤销 VibeKits 托管的控制端 SSH 公钥；不得删除用户原有 SSH 公钥，也不影响本地 Harness、项目、会话、插件市场及普通远程协助。
6. macOS 与 Windows 共用 Flutter 业务逻辑、协议、状态机和验收用例；平台差异只放在原生适配层。
7. “远程”是正式能力而不是局域网别名：控制端与被控端处于不同 NAT、不同运营商或不同城市时，必须自动从直连回退到 HBBR，并保持与局域网 P2P 相同的 MCP、SSH/SFTP、应用调试和 ADB 能力。

## 3. 非目标

- 不传输桌面画面，不实现远程鼠标键盘，不复刻 RustDesk 远程桌面 UI。
- 不把系统 SSH、Remote Login、IP、端口、用户名、密码、密钥或证书变成用户前置条件。若某平台适配层内部复用系统调试设施，也必须由 VibeKits 封装和检查，不能增加用户操作步骤。
- 不允许仅凭 ID 绕过 A 的授权开关。
- 不把“中继在线”“端口已监听”伪报为已经连接或调试成功。

## 4. 用户交互

本机 ID、连接历史、协同开关和仿真开关统一放在“设置 → 高级”的独立管理页面。同一管理页面保留两个互不替代的授权域：

- “远程协助”：共享 Harness 项目、会话、推理和结构化操作。
- “允许作为仿真机”：共享设备调试工具，不共享桌面画面。

VibeKits 内部的两个授权域共用同一 VibeKits ID 和同一 `VibekitsHarness` 网络进程，但权限、端点和关闭动作独立。这不得与独立的 KEMI 远程办公 App 共用进程、配置或 IPC。仿真机开关必须封装全部被控端准备工作：用户只打开一次，不再打开 LAN MCP、SSH、插件、端口或其他权限页面。开关打开后显示“仿真机可连接”；存在有效协议连接时显示绿点和调用方 ID；异常显示可操作原因。用户不需要输入或复制 IP、端口、密码、密钥、证书。

控制端的唯一必填输入是 ID。标准操作只有三步：

1. A 运行 VibeKits，并打开“允许作为仿真机”；
2. 用户把 A 界面显示的 ID 告诉 B 上的大模型；
3. 大模型自动连接并开始检查 A 上指定 App。P2P、中继、工具发现、重连和本地端口分配均不得要求用户参与。

同一 ID 的控制端入口必须明确给出“协同”和“仿真”两个动作，不能用一个含义不清的“连接”按钮。选择“仿真”后，客户端必须完成传输握手、重新读取目录、执行一次目标进程只读查询，并在目标端声明的受控文件目录执行一次有界文件查询；四项全部成功后才显示绿色“仿真调试已连接”。

Harness 工作区只显示只读状态，不承担任何远程管理操作：远程协助开关关闭且没有控制端会话时不显示协同状态；开关打开但尚未完成认证、授权范围、项目订阅和有效心跳时显示蓝色“协同等待连接”；只有真实远程 Harness 数据通道持续提供有效心跳时才显示绿色“协同已连接”；已打开能力发生真实错误时才显示“协同异常”。仿真显示“准备中 / 可连接 / 中 / 异常”，开关关闭时不显示占位或异常。状态条不得显示本机 ID、密码、开关或管理按钮。

本机 Harness 工作状态 IPC、MCP 目录观察者、KEMI 本机进程、Relay 注册成功或仅建立 RustDesk 字节隧道，都不能单独作为“协同已连接”的证据。状态发布链与远程连接链必须解耦：前者只发布工作快照，后者必须以认证后的远程数据会话和心跳为准。

协同和仿真是独立的数据传输层，禁止替换、覆盖、导航、重载或阻塞 Harness WebView，也不能改变本地项目、会话、插件市场、推理和工具调用生命周期。远程层异常时 Harness 仍须独立工作；远程状态只能降级为异常提示。

Harness 启动链只允许包含官方 DSH 进程、官方浏览器 URL 和原生 WebView。远程协助、仿真、LAN/MCP 发现只能在 Harness 首屏完成后异步启动；任一可选服务失败时不得修改 Harness 加载状态、重启其进程、清除 WebView 缓存或本地存储。

## 5. 网络与协议

1. 使用 `VibekitsHarness` 独立 RustDesk 身份、HBBS 寻址、P2P 打洞和 HBBR 回退，不依赖外部 RustDesk App 或插件。
2. 仿真机 MCP 服务固定监听执行端 `127.0.0.1:32147`；禁止绑定公网地址。
3. 设备调试同时复用系统 OpenSSH 的固定回环 `127.0.0.1:22`。VibeKits 在开关内完成服务检查/开启、控制端独立 Ed25519 密钥生成、首次目标机批准、公钥写入和主机指纹固定；用户不配置地址、端口、账户、密码或密钥。
4. 控制端通过固定目标 `32147`（MCP）与 `22`（桌面系统 SSH）建立受管隧道；Android 仿真机还可通过固定回环 `127.0.0.1:5555` 建立 ADB 隧道。调用方只提供设备 ID，不能指定任意远端地址或端口。隧道退出、授权关闭或连接失效时，本地端口必须关闭。
5. MCP 隧道使用 `2025-06-18` JSON-RPC；SSH 隧道必须启用 `BatchMode`、`IdentitiesOnly`、严格 `known_hosts`，并把扫描到的 Ed25519 指纹与已认证 MCP 通道返回的指纹逐字核对。
6. 所有调用记录调用方、工具、脱敏参数摘要、开始/结束时间、结果和错误码；不得记录私钥、令牌或文件正文。

### 5.1 广域网等价性

- 调用方只提交统一数字 ID；不得要求公网 IP、动态域名、路由器映射、VPN、公开 SSH 端口或手工选择中继服务器。
- 同网时优先 P2P；跨网打洞失败必须自动使用 HBBR 原字节中继。上层 MCP/SSH/ADB 不得因承载方式变化而切换协议、减少工具或要求用户重新授权。
- UI 和审计必须显示本次是“直连”还是“中继”，但这只是状态信息，不增加连接步骤。
- 广域网可用的前提仅为两端能访问配置的 HBBS/HBBR、被控端授权开关打开且设备 ID 已由服务器确认。服务不可达、设备离线、授权关闭和中继超时必须返回不同错误。
- 发布门禁必须在两端不共享局域网的条件下，或通过只用于验收的 `forceRelay` 强制中继，完成真实初始化、目录读取、命令、双向文件、远端日志和 ADB。仅在同一 LAN 成功不能声明“远程仿真完成”。

### 5.2 与 KEMI 远程办公并行

- KEMI 远程办公与 VibeKits 必须各自独立可用。VibeKits 不得依赖远程办公进程、桌面会话、ID、配置、密码或 IPC；远程办公未安装或完全退出时，VibeKits 远程仿真仍须通过全部核心门禁。
- 两者同时运行时使用独立身份、配置目录、IPC 名称、监听端口、会话表和关闭动作。任一方启动、断开、升级或退出不得重启、覆盖、抢占或终止另一方。
- 远程办公的抓屏、录屏和人工输入可作为现场验收的辅助观察手段，但不是远程仿真的数据通道或成功证据。正式证据必须来自 VibeKits 自己的协议状态、远端工具结果和审计记录。
- VibeKits 不请求桌面画面、录屏、鼠标或键盘注入，因此不与远程办公竞争桌面采集和输入控制。远程办公正在工作时，VibeKits 仍只通过自身 MCP/SSH/ADB 通道独立完成诊断；如需人工观察，可使用已存在的远程办公会话，但 VibeKits 不自动抢占、新建、切换或关闭该会话。
- 并行验收至少覆盖“仅 VibeKits”“仅 KEMI 远程办公”“两者同时运行”三组；第三组还要验证双方持续任务、断开和重连互不影响。

## 6. 能力与权限

首期复用 VibeKits 权威工具目录，包括只读设备发现、目标 App 与进程状态、macOS Unified Log / Windows Application Event Log、崩溃报告、截图、性能采样，以及已有下载、安装、启动、停止和受控文件操作。工具目录必须描述 A 的整机能力，不能只返回 VibeKits/Harness 自身状态。工具风险等级保持不变；危险/不可逆操作仍须走工具自身的批准策略，不能因为打开仿真机开关而解除安全门禁。

普通远程协助原有协议继续禁止桌面、终端、文件及任意端口转发。远程仿真授权只开放固定回环 `32147`（MCP）、桌面系统 `22`（SSH），以及 Android 设备 `5555`（ADB）三个目标，不能把同一授权扩张成任意端口或通用网络代理。ADB 仅在目标设备已开启并授权 ADB TCP 服务时可用。

### 6.1 “调试整台机器”能力合同

打开“允许作为仿真机”后，不再要求用户逐项打开工具。目标端必须一次性公开当次运行版本的完整可执行 MCP 目录，控制端连接后重新读取目录，不能使用历史缓存。最少必须覆盖：

| 任务 | 目标端真实数据/动作 | 首期稳定工具 |
|---|---|---|
| 发现任意 App | 进程、PID、父进程、CPU、内存、运行时长、命令行 | `vibekits.device.processes` |
| 定位运行异常 | macOS Unified Log / Windows Application Event Log | `vibekits.device.logs` |
| 定位崩溃 | macOS DiagnosticReports / Windows CrashDumps 元数据 | `vibekits.device.crash_reports` |
| 复现和恢复 | 启动、停止指定 App | `vibekits.device.app_control` |
| 系统状态 | CPU、内存、磁盘、Top 进程和连续采样 | `vibekits.system.resources` 及权威目录中的系统诊断工具 |
| 工程与文件证据 | 哈希、差异、搜索、受控下载及既有工程工具 | 权威目录中的 `vibekits.file_*`、Git、网络与工程工具 |
| 通用真机调试 | 上传/下载调试候选、运行受批准命令、读取目标文件和构建产物 | `vibekits.simulator.upload_file`、`vibekits.simulator.ssh_exec` 与固定 SSH/SFTP 隧道 |
| 安装其他 App | 校验签名、包身份和 SHA-256，保留回滚后安装或可恢复卸载 | `vibekits.device.applications`、`vibekits.device.app_install`、`vibekits.device.app_uninstall` |
| 更新 VibeKits 自身 | 签名候选流式上传、验证、替换、重启和回滚 | `vibekits.simulator.install_candidate` 与 `vibekits.device.update_*` |

安装能力必须按目标类型分开验收：目标机连接的 Android 设备继续使用已有 ADB 推送、拉取和签名 APK 安装工具；VibeKits 自身使用同团队签名候选协议；其他 macOS 产品只接受签名、通过 Gatekeeper 且身份匹配的单 App ZIP，Windows 只接受 Authenticode 发布者匹配的 MSI。通用 SSH 命令与文件传输用于经批准的诊断和开发流程，不能绕过安装工具的签名、身份、回滚和审计门禁。

目标机用户打开“远程仿真”开关即完成一次性持久授权。此后，同一 VibeKits 控制端 ID 通过固定回环仿真端点执行已包含范围内的状态读取、文件、SSH、安装和卸载操作时不得逐次弹出应用内批准；关闭开关立即撤销该授权。控制端身份变化、授权范围扩大或用户主动撤销时必须重新确认。操作系统自身要求的管理员认证、隐私许可或安全确认仍由系统负责，VibeKits 不得绕过。

这些工具执行在 A，不得把 B 的本机结果伪装成远端结果。读取类工具在授权开关有效期内可直接执行；写入、应用启停、安装和升级仍保留工具风险标记、审计和明确结果。开关关闭后整个端点失效，而不是逐个工具残留。

### 6.2 解决问题而不只“看状态”

标准闭环必须是“发现目标 App → 采集远端证据 → 本地源码分析/修复 → 构建签名候选 → 传到同一 ID → 远端重启复现 → 再次读取日志与状态 → 必要时回滚”。控制端可以在每次有审计和风险批准的前提下使用 SSH/SFTP，但用户侧只操作一个仿真开关和一次首次公钥批准，不能要求用户手工配置 SSH。

## 7. 状态机

`关闭 → 启动网络 → 注册 ID → 启动回环端点 → 可连接 → 已连接/调用中 → 可连接`。

任何阶段失败都进入“异常”，保留同一 ID，并允许重试。关闭动作从任意状态进入“正在关闭”，先停止接受请求，再关闭端点和隧道，最终回到“关闭”。旧 generation 的迟到回调必须丢弃。

## 8. 兼容性和升级

- 仿真机层只依赖稳定的 RustDesk 字节隧道和 MCP 标准，不修改官方 Harness DOM，不覆盖插件市场和官方侧栏。
- ID、授权域和端口以版本化常量管理。协议新增能力只扩展 MCP tools/capabilities；旧客户端看不到新工具但仍能连接。
- macOS Release 必须支持 Apple Silicon 与 Intel、macOS 12+，完成 Developer ID 签名、公证和 Gatekeeper；Windows Release 必须在 D 盘真机环境安装启动并完成基础性能门禁。
- VibeKits macOS 候选升级使用两阶段合同：`begin` 生成五分钟有效、单次使用且绑定文件名/字节数/SHA-256 的随机令牌；只允许经仿真隧道到达的回环 `PUT /vibekits-simulator/v1/update` 流式上传；`apply` 再验证单一 `Vibekits.app` 根目录、包名、递增构建号、相同 Developer ID Team、Universal 双架构、最低 macOS 12、完整代码签名。替换前保留唯一回滚副本，失败必须恢复旧 App。
- 通用 LAN MCP 端点即使在本机也必须拒绝候选上传。上传路由只在“允许作为仿真机”生成的专用回环端点存在，避免把升级能力暴露成局域网文件写入口。
- 升级协议加入目标端的版本不能倒推安装到旧版本：不含 `vibekits.device.update_*` 的旧目标需要一次人工安装作为引导；完成一次引导后，后续版本才能做到只给 ID 的签名升级。这一边界必须在交付记录中写明，不能假报远程更新成功。

## 9. 闭环验收

1. 默认关闭：重启后显示同一 ID，`32147` 不监听，远程调用失败为明确的未授权。
2. 打开：3 秒内显示“仿真机可连接”，MCP 只监听 `127.0.0.1:32147`；系统 SSH 端口由开关统一准备，不要求用户另行设置。
3. 同 ID：远程协助页面 ID、仿真机页面 ID、HBBS 实际 routingId 完全一致。
4. 真双机：B 仅输入 A 的 ID，建立 P2P；强制中继再做一轮。两轮分别完成初始化、工具列表、只读设备查询和一项受控应用操作。
   强制中继轮必须继续完成 SSH 命令、SFTP 双向小文件哈希，以及远端 ADB `devices`、`shell getprop`、有界 `logcat`、push/pull 和测试 APK 安装；结果必须来自 A 及其连接的 Android 设备。
5. 故障诊断：A 上制造可恢复的测试 App 异常，B 取得日志/崩溃/性能证据并定位；结果不得来自 B 本机。
6. 撤销：调用中关闭开关，旧连接在限定时间内失效，新调用被拒绝，VibeKits 托管公钥全部移除且用户原有公钥保持不变；普通远程协助和本地 Harness 保持可用。
7. 回归：插件市场、MCP、本地 ADB、项目/会话增删改拖动、并行会话、停止、时间线、应用中心均通过既有回归。
8. 升级：普通 LAN 端点拒绝上传；仿真专用端点完成令牌绑定、流式传输、SHA 校验；篡改、同版本、错包名、错 Team、非 Universal、最低系统高于 12 任一条件均拒绝；有效候选替换后同一 ID 恢复并可再次调用诊断工具。
9. 共存：分别在远程办公退出、单独运行和抓屏/录屏会话进行中执行 VibeKits 仿真；三种情况下核心工具一致，双方启动、停止和断线恢复互不影响。

只有上述真双机证据、平台构建与回归全部通过，才能声明“统一 ID 仿真机访问已完成”。

## 10. 平台角色矩阵

## 11. 控制端连接器契约

### 11.1 将目标目录挂载到控制端（2026-09-24 Mac 实测）

此功能的入口仍是目标设备的 VibeKits 数字 ID；目标端先开启“允许作为仿真机”并完成首次 SSH 公钥批准。控制端通过 `vibekits.simulator.connect` 确认 `connected=true`、目标身份、主机指纹及 `p2p_or_relay`，再使用连接器建立的**本机回环 SSH 端口**。该端口是每次连接分配的临时端口，不是目标机的公网 SSH 端口；必须遵守本规范的固定端点、严格 `known_hosts` 和受管密钥约束。不得为了挂载另外暴露 SSH、索取密码，或以远程桌面代替仿真通道。

2026-09-24 在 Mac 控制端与 `4456560334` Mac 目标端验证的链路是：

```text
目标 /Users/mac/kemi/vibekits
  → VibeKits 受管 P2P/HBBR SSH 隧道（控制端 127.0.0.1:动态端口）
  → rclone SFTP 后端（限定到该目标目录）
  → rclone serve webdav（仅监听控制端 127.0.0.1:38445）
  → macOS mount_webdav
  → 控制端 /Users/newlink/VibeKits-4456560334
```

这是一种**控制端临时文件系统映射**，并未把目标磁盘复制或迁移过来。映射建立前应先验证 SFTP 可以读取指定目录；挂载后在两侧各创建一个无害测试目录，验证双向可见与写入，再清理测试目录。此次远端新建目录最初因 rclone 默认目录缓存而延迟可见；将 `--dir-cache-time 2s --poll-interval 0` 用于 WebDAV 服务后，复验约 4 秒可见。Finder 刷新不是远端数据丢失的证据。挂载依赖仿真连接、rclone 服务和本机挂载进程；任一退出应卸载并关闭本机服务，重新连接时重新验证身份与动态端口。当前并无自动重连或开机自动挂载验收。

Windows 控制端可以复用**同一个 VibeKits SSH 隧道和 rclone SFTP 后端**，但不能使用 macOS 的 `mount_webdav`。推荐在已安装 WinFsp 的 Windows 上用 `rclone mount <受管SFTP远端>:<目录> <空闲盘符> --dir-cache-time 2s --poll-interval 0` 呈现给资源管理器；从非提权的用户会话启动，避免提升权限创建的盘符在普通资源管理器中不可见。Windows 原生 WebDAV 也是一种客户端，但其 HTTP Basic 认证默认受系统限制，不应为使用本机 HTTP 映射而放宽系统注册表认证策略。无论采用哪种呈现方式，WebDAV 如启用必须只绑定回环地址，不能成为 LAN/公网文件服务。Windows 的目录双向写入、文件锁、断线恢复、盘符可见性和卸载清理**尚未真机验收**，不能把 Mac 实测当作 Windows 已完成。

操作说明只记录目录、流程和非敏感参数；不保存隧道令牌、SSH 私钥、凭据、临时端口或用户文件内容。rclone 的 Windows 挂载依赖与权限边界见 [rclone mount 文档](https://rclone.org/commands/rclone_mount/#installing-on-windows)，WebDAV 服务及 Windows 客户端限制见 [rclone serve webdav 文档](https://rclone.org/commands/rclone_serve_webdav/#access-webdav-on-windows)。本次实际验收细节见 [dev.236 远程目录映射记录](acceptance/V1_9_0_DEV236_MAC_RELEASE_REMOTE_MAP_2026-09-24.md)。

面向大模型的连接器只接收 `routingId`；`forceRelay` 只允许在内部验收接口使用。本地空闲端口由连接器自动分配，远端目标固定为 `127.0.0.1:32147`、桌面系统 `127.0.0.1:22`，以及 Android 设备 `127.0.0.1:5555`；任何调用方都不能传入，防止把该能力滥用为任意代理。连接过程必须依次产生：

1. `listener_ready`：控制端回环监听已建立，但尚不能调用；
2. `transport_connected`：HBBS/HBBR/P2P 登录与远端授权均完成。由于 RustDesk 端口转发按首个本地 TCP 请求启动，控制端必须并发发起唯一一次真实 MCP 初始化和等待该状态；只有两者都成功才可向上层报告“已连接”，不得先建一次空探测连接；
3. 明确失败码：参数错误、远端离线、权限关闭、传输超时或进程异常；
4. 连接器退出：本地监听随进程关闭，不保留后台幽灵隧道。

MCP 初始化成功后，客户端必须先读取工具目录和能力摘要，再按原工具风险等级调用；不得把客户端缓存的旧目录当作当前设备能力。

## 12. 安全边界与审计

- 开关只授权 VibeKits 固定设备工具端点、桌面系统固定 SSH 调试端点及 Android 设备固定 ADB 调试端点，不授权远程桌面或任意 TCP 转发；协议层只允许访问固定回环 MCP `32147`、SSH `22` 与 Android ADB `5555`。
- 本机服务仅绑定 IPv4 回环；局域网扫描 `32147` 不应得到监听端口。
- 原生权限位在传输进程启动时为关闭；App 根据用户保存的显式选择恢复。传输进程崩溃或被替换后不会继承内存权限位。
- 只有端点、权限位、同一 routing ID 和 HBBS 注册状态全部真实就绪，UI 才显示“仿真机可连接”。
- 只有原生连接表出现 `authorized=true`、`disconnected=false` 且端点属于 `127.0.0.1:32147`/`127.0.0.1:22`/`127.0.0.1:5555` 时，UI 才显示绿色“仿真机已连接”和调用方 ID；Android ADB 另需本地 `adb connect` 与 `getprop` 成功才显示 ADB 就绪。
- 日志保留错误码、耗时和脱敏参数摘要；密码、密钥、令牌、文件正文及模型上下文不得进入连接日志。

## 13. 实现拆分

1. Flutter 授权层：在“设置 → 高级”保存独立开关与管理数据；Harness 只订阅只读状态灯和错误文案。
2. 本机工具层：启动固定回环 MCP 端点，复用权威工具目录和批准策略；提供针对其他 App 的进程、日志、崩溃、性能及应用生命周期工具。
3. RustDesk 宿主层：同一 ID 注册、易失原生门禁、固定端点自动授权、真实连接元数据。
4. 控制端层：公开接口只收 ID，内部启动专用隧道，区分“监听完成”和“传输完成”，自动初始化 MCP、读取工具目录并向智能体提供连接/状态/目录/调用/断开五个稳定操作。
5. 发布层：macOS 主程序与 helper 都必须是 Universal；Windows helper 必须随 App 内置；构建脚本对架构、协议状态标记和许可证执行硬校验。

RustDesk 被控端处理固定仿真端点时，必须在通用桌面 Connection Manager IPC 之前完成本地授权开关校验、固定端点限制、目标 ID 校验和登录响应。`VibekitsHarness` 是独立字节隧道宿主，不存在桌面 CM；等待桌面 IPC 会使已经到达被控端的连接永久卡住。调用登录响应函数前也不得预先把连接标成 `authorized=true`，否则通用响应函数会按“已响应”短路，控制端收不到登录成功消息。

## 14. 交付阶段

- M1：需求、威胁边界、状态机和协议常量冻结。
- M2：macOS/Windows 被协助端开关、固定端点和原生权限门禁完成。

## Android 被仿真扩展（2026-09-22）

Android 不再仅作为控制端；设置→高级应提供独立“允许作为仿真机”开关及本机统一 ID，默认关闭。继续保留对其他设备的控制能力，不因此自动开启 Harness 远程协助。
开关必须贯通 Flutter→Android 私有服务→Rust 原生入站授权；只开放固定回环 MCP/控制端点，不开放桌面、任意端口或未授权 SSH。关闭后先拒绝新调用并关闭现有端点。连接状态必须依据真实入站连接，不能用空数组占位。
Android 系统信息、应用、日志、文件与安装必须遵守系统权限；未授予的能力明确返回不支持或权限不足，不能伪装拥有 root/ADB 全机权限。验收使用 63 的实际统一 ID 从另一端调用工具，ADB 安装成功不算被仿真成功。
