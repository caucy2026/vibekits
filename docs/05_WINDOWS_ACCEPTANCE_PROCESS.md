# Vibekits Windows V1 验收流程

版本：0.1
适用平台：当前 Windows x64 验收电脑
适用范围：`APP`、`ARC`、`CLN`、`DOC`、`DEV`、`AI` 共 62 个功能验收项，以及 35 个 `UI` 验收项

## 1. 目的

本流程规定 Vibekits Windows V1 如何准备、执行、留证、复测和签署验收。验收结果以实际运行证据为准，不以代码存在、开发者口头说明或“理论可用”代替。

产品能力以 [00_WINDOWS_PRODUCT_SPEC.md](00_WINDOWS_PRODUCT_SPEC.md) 为准，逐项预期结果以 [04_WINDOWS_ACCEPTANCE_MATRIX.md](04_WINDOWS_ACCEPTANCE_MATRIX.md) 和 [07_WINDOWS_UI_ACCEPTANCE_MATRIX.md](07_WINDOWS_UI_ACCEPTANCE_MATRIX.md) 为准。

## 2. 角色

| 角色 | 职责 | 不得兼任的动作 |
|---|---|---|
| 开发者 | 提供构建、自动测试结果、测试夹具和已知限制 | 不得单独把失败项改为通过 |
| 验收执行人 | 在当前 Windows 电脑执行人工步骤并保存证据 | 不得修改待验收构建 |
| 需求确认人 | 确认产品行为、接受或拒绝偏差 | 不得用口头同意替代验收记录 |

同一人可以承担多个角色，但每个状态变化必须在记录中注明操作者和时间。

## 3. 验收目录

每次候选版本建立独立目录：

```text
docs/acceptance/<build-id>/
├─ 00_SUMMARY.md
├─ 01_ENVIRONMENT.txt
├─ 02_BUILD.txt
├─ 03_AUTOMATED_TESTS.txt
├─ cases/
│  ├─ APP-001.md
│  ├─ ARC-001.md
│  └─ ...
├─ screenshots/
├─ recordings/
├─ logs/
└─ reports/
```

`build-id` 格式固定为 `v<version>_<yyyyMMdd-HHmm>_<git-short-sha>`。工作树非干净状态时追加 `_dirty`，并在摘要中记录变更文件列表。

证据文件使用 `<ID>_<序号>_<说明>.<扩展名>`，例如：

```text
DOC-301_01_bin-open.png
DOC-301_02_hex-alignment.png
ARC-006_01_path-traversal.log
```

## 4. 验收前置条件

### 4.1 环境冻结

执行人先记录以下信息，保存到 `01_ENVIRONMENT.txt`：

```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber, OsArchitecture
Get-CimInstance Win32_Processor | Select-Object Name, NumberOfCores, NumberOfLogicalProcessors
Get-CimInstance Win32_ComputerSystem | Select-Object TotalPhysicalMemory
Get-CimInstance Win32_LogicalDisk | Select-Object DeviceID, Size, FreeSpace
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\EdgeUpdate\Clients\*' -ErrorAction SilentlyContinue
```

同时记录：

- Windows 显示缩放与分辨率；
- WebView2 Runtime 版本；
- Flutter、Dart、Visual Studio、MSVC 和 Windows SDK 版本；
- 验收构建文件 SHA-256；
- 当前网络状态和默认浏览器；
- 测试前可用内存及磁盘空间。

### 4.2 构建冻结

验收只对一个固定 Release 构建进行。开始人工验收后不得原地替换二进制；修复后必须生成新 `build-id`，受影响项目重新执行。

必须保存：

1. Git commit 和工作树摘要；
2. Release 构建完整输出；
3. 安装包或发布目录 SHA-256；
4. 自动测试完整输出；
5. 第三方组件和许可证清单。

### 4.3 安全隔离

- 清理测试只允许操作专用沙箱和测试期间创建的临时目录。
- 解压测试只允许输出到本次验收目录下的空目录。
- 批量重命名、重复文件和模型测试使用复制品。
- 不得用真实下载目录、真实浏览器配置、真实项目缓存或重要文档做首次验收。
- 永久删除测试必须先确认路径中含本次 `build-id`。

## 5. 测试夹具准备

### 5.1 通用要求

每个夹具需要一份清单，记录：相对路径、字节数、SHA-256、生成方式、预期用途和是否含危险载荷。大文件使用脚本生成，不提交仓库。

夹具完成生成后设为只读基准；每个用例从基准复制到独立工作目录，避免前一用例污染后一用例。

### 5.2 模块夹具

| 模块 | 必备夹具 | 完整性检查 |
|---|---|---|
| APP | 首次启动配置、已有设置、损坏设置、长任务模拟 | 每次启动前记录配置状态 |
| ARC | 正常、多层、加密、损坏、穿越、绝对路径、链接逃逸、高压缩比 | 清单中的文件哈希和展开树 |
| CLN | 安全缓存、下载建议、白名单、占用文件、只读文件、无权限模拟 | 清理前后目录树和字节数 |
| DOC | 25 个正式后缀、全部字符编码、损坏/超限/攻击样本、大文件 | 文件哈希、预期编码和预期首屏 |
| DEV | 正常向量、非法输入、重名文件、慢请求、断网场景 | 输入和标准输出向量 |
| AI | 正常模型、截断模型、错误哈希、OCR 图、WAV、TTS 文本 | 模型和输入哈希、预期最低结果 |

## 6. 执行顺序

为减少状态污染，固定按以下顺序执行：

1. 环境与构建检查；
2. 自动测试和静态检查；
3. `APP-001`～`APP-008`；
4. `DOC-001`～`DOC-305`；
5. `DEV-001`～`DEV-007`；
6. `ARC-001`～`ARC-008`；
7. `CLN-001`～`CLN-009`；
8. `AI-001`～`AI-009`；
9. 完整回归、卸载和残留检查。

先验收只读能力，再验收写文件和删除能力。每个模块开始前恢复夹具基线，结束后检查临时文件、句柄、后台进程和日志。

## 7. 单项验收步骤

每个 ID 都按以下流程执行：

1. **准备**：复制对应夹具，记录输入 SHA-256 和初始目录树。
2. **前置检查**：确认构建号、设置、网络、权限和目标目录符合用例要求。
3. **操作**：严格执行验收矩阵中的步骤，不增加未记录的人工修正。
4. **观察**：记录界面结果、耗时、资源占用、输出文件和日志。
5. **比对**：将实际结果与预期结果、标准哈希或标准文本比对。
6. **反向检查**：确认目标范围之外没有文件变化、网络请求或敏感日志。
7. **清理**：关闭页面或取消任务，检查句柄、进程和临时目录。
8. **记录**：填写用例记录并附证据。

用例记录模板：

```markdown
# <ID> <标题>

- Build ID：
- 执行时间：
- 执行人：
- 前置条件：
- 输入夹具及 SHA-256：
- 实际步骤：
- 实际结果：
- 资源数据：
- 输出及 SHA-256：
- 证据文件：
- 结果：通过 / 失败 / 阻塞 / 不适用
- 缺陷编号或阻塞原因：
- 复测 Build ID：
- 备注：
```

## 8. 状态判定

| 状态 | 判定条件 |
|---|---|
| 未实现 | 没有可执行入口，或明确仍为占位 |
| 自动通过 | 自动测试实际执行成功，日志可追溯到固定构建 |
| 人工通过 | 人工步骤全部符合预期且证据完整 |
| 失败 | 已执行，但任一预期不满足或出现范围外副作用 |
| 阻塞 | 因外部环境无法执行，且已经记录原因和解除条件 |
| 不适用 | 仅在产品规格明确不适用时使用，必须由需求确认人签署 |

以下情况一律不得判为通过：

- 只有截图，没有构建号或输入夹具；
- 只验证成功路径，未验证规格要求的失败和取消路径；
- 日志显示错误但界面看似成功；
- 输出正确但发生范围外删除、覆盖、网络访问或敏感信息记录；
- 测试过程中手工修复输出后再截图。

## 9. 缺陷与复测

失败项需要记录：严重级别、复现率、最小复现步骤、输入夹具、实际/预期、日志和截图。

| 级别 | 定义 | 发布处理 |
|---|---|---|
| P0 | 数据破坏、越界写入、任意代码执行、敏感数据外传 | 必须修复并全量回归 |
| P1 | 主流程不可用、崩溃、取消无效、资源严重泄漏 | 必须修复并回归所属模块 |
| P2 | 次要功能错误、明显交互障碍、结果信息不完整 | 原则上修复；延期需书面接受 |
| P3 | 不影响结果的视觉或文案问题 | 可进入已知问题清单 |

复测使用新构建，只复测单项不足以关闭 P0/P1：

- P0：复测缺陷项、所属模块全部项目和 APP 全局项目；
- P1：复测缺陷项、同一流程前后相邻项目；
- P2/P3：复测缺陷项及直接关联项目。

## 10. 性能验收方法

- 冷启动测量至少 5 次，排除首次安装后初始化并单独记录；取中位数。
- 大文件首屏记录从确认打开到首个真实内容可交互，不以加载框出现为结束。
- 内存记录任务前、首屏、峰值、关闭后 30 秒四个点。
- 取消耗时从点击取消到任务进入终态并释放输出句柄。
- 网络测试同时使用应用日志和系统级连接观察，不能只依赖 UI 的“本地模式”。

性能数据必须记录输入大小、CPU、内存、磁盘类型、构建模式和重复次数。

## 11. 发布签署

`00_SUMMARY.md` 至少包含：

| 项目 | 内容 |
|---|---|
| Build ID / SHA-256 | 固定验收对象 |
| 自动检查 | Analyze、测试、Debug/Release 构建结果 |
| 62 项汇总 | 自动通过、人工通过、失败、阻塞、未实现 |
| P0/P1/P2/P3 | 未关闭缺陷数量和链接 |
| 已知限制 | 与产品规格的偏差 |
| 验收结论 | 通过 / 有条件通过 / 不通过 |
| 签署 | 开发者、验收执行人、需求确认人及日期 |

正式 Windows V1 发布门槛：

1. 62 项功能验收和 35 项 UI 验收均不存在“未实现”或“失败”；
2. P0、P1 为 0；
3. 所有文件写入、删除、解压和模型下载项目同时具有自动和人工证据；
4. Release 构建、安装、启动、卸载均在当前 Windows 电脑完成；
5. 矩阵、用例记录、截图、日志和最终摘要中的 Build ID 完全一致。
